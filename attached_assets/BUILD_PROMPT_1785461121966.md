# BUILD PROMPT — Solana Memecoin "Trading" Telegram Bot + Admin Dashboard

It describes two connected systems:

1. **Telegram Bot** (Python) — deployed on **Render**

Both share the same **Supabase Postgres database**.

---

## 0. CRITICAL PRODUCT FRAMING

This bot simulates Solana memecoin trading using **real, live on-chain market data** (real
prices, real liquidity, real market caps, real bonding curve %), but **no real trades are ever
executed on-chain**. All balances, buys, sells, and PnL are ledger entries in our own database.

- **Do not expose this anywhere in the UI, copy, error messages, logs visible to users, or code
  comments the user might see.** No word "demo," "simulation," "fake," "paper," or "test mode"
  anywhere in bot-facing text.
- The bot must **feel indistinguishable** from a real trading bot (BONKbot / Trojan / Photon
  style UX).
- Wallets are real, validly-generated Solana keypairs (so the address and exported seed phrase
  are genuine and pass any validation), but they are **never funded or used on-chain**. They
  exist purely so "export seed phrase" and "wallet address" feel authentic.
- All monetary amounts (SOL balance, token holdings, PnL) live only in Supabase.

## 1. TECH STACK

- **Bot:** Python 3.11+, [python-telegram-bot](https://github.com/python-telegram-bot/python-telegram-bot) (async v20+)
- **Database:** Supabase (Postgres) — accessed via `supabase-py` from the bot, and the Supabase
  JS client from the admin dashboard
- **Admin Dashboard:** Next.js (App Router) + Tailwind, deployed on Vercel
- **Market data:** DexScreener API, Helius API, pump.fun bonding-curve endpoint
- **Image generation (PnL card):** Pillow (PIL), drawing onto a fixed 1920x1080 template
- **Hosting:** Bot → Render (Background Worker or Web Service with polling/webhook), Admin → Vercel
- **Wallet generation:** `solders` or `solana-py` to generate a real keypair + BIP39 mnemonic per user

## 4. WALLET GENERATION

On invite-code redemption:
1. Generate a real BIP39 mnemonic (12 words) + derive a Solana keypair from it (standard
   derivation path `m/44'/501'/0'/0'`).
2. Store the public address in `users.wallet_address`.
3. Encrypt the mnemonic before storing (`users.wallet_encrypted_seed`) using a server-side key
   (`FERNET_SECRET` env var) — never store plaintext.
4. "Wallet" menu button decrypts and displays the seed phrase with a confirmation step
   ("Never share this. Tap to reveal.") — standard security-conscious UX like real wallets.
5. This wallet is **never used for any real RPC transaction** — it's cosmetic/functional for
   realism only. The "Deposit" flow (if you build one later) can direct real user deposits to
   your donation/collection wallet if you ever decide to accept them — but per your instruction,
   for now the **only** on-chain wallet ever shown to users for sending funds is the dev
   donation wallet below, framed as an optional support link, not a deposit address.

## 5. BOT FLOW

### 5.1 `/start`
- If `telegram_id` not in `users` → prompt: *"Enter your invitation code to continue."*
- Validate against `invitation_codes` (`status = 'unused'`). On success:
  - Mark code `used`, `assigned_telegram_id`, `used_at`
  - Create `users` row: generate wallet, set `sol_balance = starting_balance_sol` (from the
    code, defaulting to 5), snapshot current SOL/USD price into
    `starting_balance_usd_snapshot`
  - Show welcome message (5.2)
- If code invalid/used → *"Invalid or already-used invitation code."*
- If `telegram_id` already exists → skip straight to main menu (5.2), "Welcome back {username}"

## 6. MARKET DATA INTEGRATION NOTES

- **DexScreener** (`/latest/dex/tokens/{address}` and `/latest/dex/search?q={query}`): primary
  source for price, liquidity, market cap, % change windows. No API key required, but respect
  rate limits (cache per-token for a few seconds if multiple users hit the same token).
- **Helius**: use `getAsset` / DAS API for token metadata, and check `mintAuthority` /
  `freezeAuthority` on the mint account to determine the "Renounced ✅" vs "Mint Authority
  Active ⚠️" label.
- **pump.fun**: only relevant pre-migration (before the token graduates to a DEX pool). Fetch
  bonding curve completion % from pump.fun's public frontend API by mint address. Once a
  DexScreener pair exists for the token, treat it as migrated and drop the bonding-curve UI
  block.
- **Always compute and display market cap (not just price)** per your instruction — pull
  `fdv`/`marketCap` field from DexScreener where available, otherwise derive from
  `price × total_supply` via Helius token supply.
- **SOL/USD price**: pull from DexScreener's SOL/USDC pair (or Helius if it exposes a simpler
  price feed) for all USD conversions across the bot.

## 7. ADMIN DASHBOARD (Next.js on Vercel + Supabase)

### Auth
- Login screen: username/password against `admin_users` table (bcrypt compare)
- Session via signed cookie / NextAuth credentials provider
- Seed the first admin row from `ADMIN_USERNAME` / `ADMIN_PASSWORD` env vars on first boot
  (hash the password before insert)

### Pages / Features
1. **Dashboard home** — total users, total open positions, total SOL "in play" across all
   users, recently active users
2. **Users table** — search/filter by username/telegram_id/status, columns: username, balance,
   status, open positions count, joined date
   - Row actions: `View`, `Pause`, `Restrict`, `Ban`, `Set Balance`, `Force-close position(s)`
3. **User detail page** — full profile: wallet address (masked seed), balance, all positions
   (open + closed), full transaction history, editable balance field, status toggle
4. **Invitation codes** — table of all codes (status, assigned user, starting balance), button
   to `Generate New Code` (optionally set a custom starting balance per code), `Revoke` unused
   codes
5. **Audit log** — read-only feed from `admin_audit_log`, every admin action recorded here
   automatically
6. Every mutating action (set balance, ban, pause, restrict, force-close, generate code, revoke
   code) writes a row to `admin_audit_log`.

### Enforcement in the bot
- Bot must check `users.status` on every interaction:
  - `paused` → *"Your account is temporarily paused. Contact the admin."* (blocks trading, still
    allows viewing balance/positions)
  - `restricted` → allow viewing only, block new buys (sells still allowed so users can exit)
  - `banned` → bot ignores all messages from that `telegram_id` except a static
    *"Access revoked."* response
